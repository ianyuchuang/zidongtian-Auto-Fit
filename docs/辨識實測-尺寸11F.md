# 辨識實測 — 尺寸11F（LLM API，2026-09-03）

本地模型的實驗計畫與結果在專案文件 `辨識模型實驗計畫.md`；這份是 **LLM API 路線**的實測。
重現方式：Cowork 開 Haiku／Sonnet 子代理，餵與網頁完全相同的提示詞與前處理（EXIF 轉正、長邊 1500px、JPEG q90）。金鑰不出瀏覽器，所以不是直接打 API，但輸入與指令一致。

## 素材
- 照片：`需求及資訊來源/來源資料夾範例/尺寸11F` 12 張。原檔只有 1477×1108，**1500px 上限沒有作用**。

## 結果

| 條件 | 設計＋實際兩欄都對 | 位置編號對 |
|---|---|---|
| Haiku 4.5 整張（當時的預設） | **0 / 11** | 3 / 11 |
| Haiku 4.5 先裁到白板 | 2 / 4 | 3 / 4 |
| **Sonnet 5 整張** | **9 / 12** | 11 / 12 |
| Sonnet 5 先裁到白板 | 原本讀錯的那張變全對 | — |

Haiku 的壞法固定：欄位錯位（標準值抄進實際值）、數字幻覺（`5564×50`、`4+3 x 182`、`87.5/15cm`）、或整個空白。**信心值不可信**——有一張三欄全錯卻自報 68%。Sonnet 讀錯的三張都只差一個數字，自報信心 55–75%，與實際表現相符。

根因是**白板在畫面裡太小**（約佔畫面四分之一），手寫字只剩幾十像素高，小型視覺模型讀不動。與本地模型實驗「懷疑是解析度問題」的推測一致。

## 因此改了什麼
- `api/providers.js`：Claude 預設挑 **Sonnet**（`prefer: ['sonnet']`，關鍵字比對而非寫死版本）。Gemini／OpenAI 未實測，但同理不預設挑最小的型號。
- `recognizer/prompt-default.js`：預設提示詞把欄位對應講死（位置屬內容說明、標準值格裡只有尺寸那行是設計、兩格數字很像也不可互抄），對應 Haiku 最常犯的錯。
- `state.js`：低信心不再只看模型自報信心——先過 `fieldWarnings()` 的欄位健全度檢查（空欄、推託話、設計與實際數字個數對不上），任何一項不過直接算低信心；門檻由 70 提高到 85；沒給信心也算低信心。
- `imaging.js`：白板對照圖的 bbox 四邊外擴 15%（`CROP_PAD`），框到整張（>90%）或小於畫面 2% 就當作沒框到、不裁（`usableBbox`），右欄改說明是哪一種情況。
